# VL53L8 v1.2.0 Validation And Resolved Bugs

## Scope

This note captures the final v1.2.0 consolidation work for the one-rear-sensor
OpenOtter stack:

```text
iPhone app
  -> STM32 direct BLE control
  -> B-L475E-IOT01A1
  -> one rear SATEL-VL53L8
  -> RC car throttle and steering
```

The release scope is intentionally one physically verified rear SATEL-VL53L8.
The firmware and iOS app remain ready for a future front SATEL, but physical
front/two-SATEL validation is deferred until the second board and harness are
available.

## Current Validation Status

As of 2026-06-08, user end-to-end testing went well after the latest firmware
safety selector update. The validated one-rear-sensor behaviors are:

- STM32 firmware boots and runs the main loop after the previous startup
  hardening.
- iOS STM32 diagnostics can connect to the board and render the rear VL53L8
  depth map.
- One rear SATEL-VL53L8 works in SPI mode after power-off rewiring from I2C and
  cold boot. Earlier bench work also proved I2C3 mode.
- Forward iPhone LiDAR BRAKE can be cleared by explicit reverse intent instead
  of trapping the vehicle in the forward collision state.
- Rear STM32 ToF safety no longer treats far-range non-OK VL53L8 status values
  as close obstacles.
- Firmware now protects reset/reconnect boot when the iOS STM32 debug view or
  Self Driving mode is left open; FE61 replays are queued and applied only from
  the main loop, safety ToF init waits while a fresh BLE connection is still in
  the FE41/FE44 app-handshake window, and stale BLE connections that never send
  app control are disconnected or panic-reset through `PANIC:C` if BlueNRG HCI
  is wedged.

The remaining pre-tag work is release hygiene:

- rerun PR CI after final documentation-only updates;
- optionally repeat one short hardware smoke test after the docs commit;
- merge and tag `ios-v1.2.0` and `stm32-mcp-v1.2.0` only after the user accepts
  the final validation state.

## VL53L8 Safety Policy Frozen For v1.2.0

The selected safety cells are the 4x4 row-3 center cells:

- row 3, column 2: zone index `9`;
- row 3, column 3: zone index `10`.

For v1.2.0, those cells are interpreted as:

| Selected-zone condition | Firmware class | Safety effect |
| --- | --- | --- |
| Any selected zone has status `5`, `6`, `9`, or `10` and range `1..3800 mm` | `VALID` | Feed the minimum trusted depth into the safety EMA. |
| Both selected zones have valid status and range above `3800 mm` | `CLEAR` | Report capped `3.8 m` clearance; do not feed unstable far values. |
| No trusted selected-zone depth, and any selected zone has non-valid status such as `2`, `4`, or `255` | `PARTIAL` | Treat the frame as live but degraded; hold previous EMA and do not count it as blind. |
| Sensor stream stops or driver becomes unavailable | `INVALID` through frame-gap/driver-dead policy | Fail safe through existing firmware health policy. |

This policy is deliberately conservative. The VL53L8 can still report raw debug
depths beyond 3.8 m, but the safety supervisor does not use those raw values as
precision obstacle distances.

## Release Invariants

- v1.2.0 ships with one rear SATEL physically verified.
- Rear ToF safety must never block forward escape in the one-sensor setup.
- Forward iPhone LiDAR safety must permit explicit reverse escape.
- Park is a hard safety boundary: it clears iOS-visible warning state and keeps
  stale FE43 events from reviving after Drive resumes.
- STM32 BLE callbacks must stay bounded during reset/reconnect. Attribute writes
  may queue state, but VL53L8 init/config must run from the main loop.
- Front/two-SATEL support is code-ready, documented, and host/iOS tested where
  possible, but it is not release-proven until the second sensor is physically
  installed.
